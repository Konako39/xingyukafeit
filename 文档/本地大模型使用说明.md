# 星语茶话屋使用说明

本机运行器：Ollama（本地地址 `http://127.0.0.1:11434`）

## 打开客户端

双击项目根目录的 `星语茶话屋.app`。客户端会静默启动 Ollama 后台和长期记忆 API，不会打开终端，也不会弹出 Ollama 图形客户端。

客户端包含：

- 左侧会话列表、搜索、新建和切换。
- 顶部先选择“艾莉 / 沙雅”，再选择 4B、9B、27B 档位。模型卡整张区域都可点击；换档会原地更新当前会话，不会新建对话，已有消息继续作为当前上下文。艾莉只能使用三个低审查模型，沙雅只能使用三个官方模型。
- 艾莉和沙雅各有一套严格隔离的人格记忆池；同一人格换档不丢记忆，切换人格不会串记忆。用户对话、两人的茶话、文件观察和屏幕观察都会带时间写入相应人格的池中。
- 选择、拖入或直接粘贴图片；每条最多 4 张，支持 PNG、JPEG、WebP 和 GIF。
- 流式回答和停止生成；发送后 750ms 内不会把误双击当作停止。
- 输入框上方可切换“快速 / 均衡 / 深度”：快速优先速度，均衡适合日常，深度会启用模型思考。
- 每条回复可复制、重新回答或让模型继续；回复下方显示首字耗时、总耗时、生成速度、输出 token 和完成原因。
- 顶部显示本轮长期记忆命中数量与上下文窗口占用，便于发现长对话状态。
- 会话重命名、导出、删除；人格底层设定、共享长期记忆和本会话摘要都可编辑。
- 设置中可调温度、Top P、重复惩罚、随机种子、模型常驻时间和输出上限。
- 模型加载状态、参数量、量化方式、上下文、幕后工具模型、内存释放、双 API 地址、占用统计和历史清理。
- “茶话室”页可查看两套人格池容量、艾莉与沙雅的后台交流、文件观察和屏幕观察，也可以调整频率、立即运行或分别清空记录。

图片和聊天数据只保存在 `数据/`，删除会话时会同时删除它所属的图片并回收 SQLite 空间。

## 沙雅：三个官方档位

| 档位 | 模型 | 适合场景 |
| --- | --- | --- |
| 极速档 | Qwen 3.5 4B（本地别名 `qwen3.5:4b-16k`） | 快速问答、翻译、摘要、轻量写作 |
| 日用档 | Qwen 3.5 9B（本地别名 `qwen3.5:9b-16k`） | 综合问答、较复杂写作、代码辅助 |
| 高级档 | Qwen 3.5 27B | 复杂推理、质量优先的写作和代码任务 |

## 艾莉：三个低审查档位

这组是社区制作的 Qwen 3.5 Abliterated（去拒答）版本。它显著降低安全对齐和拒答，但社区模型无法保证在所有提示下绝对不拒绝，也可能输出不准确、敏感或不适合公开场合的内容。

| 档位 | 模型 | 适合场景 |
| --- | --- | --- |
| 无审查极速档 | `huihui_ai/qwen3.5-abliterated:4b-16k` | 快速中文创作、翻译、轻量问答 |
| 无审查日用档 | `huihui_ai/qwen3.5-abliterated:9b-16k` | 高质量中文写作、综合问答、代码辅助 |
| 无审查高级档 | `huihui_ai/qwen3.5-abliterated:27b` | 质量优先的复杂创作、推理和代码任务 |

## 双人格设定

- **艾莉**：16 岁女性角色，开朗外向、机灵，带一点自然的小恶魔感；像熟悉的网友一样直率开放，偶尔顺着气氛轻轻调侃，但不会为了表演人设而辱骂、挑衅、强塞口癖或反复叫名字。她的三个档位和记忆整理器全部使用低审查模型。
- **沙雅**：16 岁女性角色，认真可靠的班长型性格，按部就班、讲原则、表达一本正经，被直接夸奖或碰到私人话题时容易害羞。

两个人格底层设定都可在“设置 → 记忆”中直接修改。

## 多模型混合记忆

一次回答由不同模型和数据层协作完成：

1. 当前选择的 4B / 9B / 27B 主模型负责回答。
2. `qwen3-embedding:0.6b-q4` 是本机从官方 FP16 原版量化得到的 Q4_K_M 向量模型，为正常对话与茶话室提供本地 RAG。它只把原文和问题转成向量、寻找语义相关片段，不生成或改写文字，因此不会因为小模型审查而拒绝艾莉侧内容；2K 检索上下文会保留长消息的开头、中段和结尾，更小的常驻体积也减少 27B 的内存竞争。
3. 两套链路各有一个隐藏 14B 质量协同模型：艾莉使用低审查 `huihui_ai/qwen3-abliterated:14b-v2`，沙雅使用官方 `qwen3:14b`。它们只做单条事实审计和窄分类，不替代三档主模型。
4. 结构化长期档案由当前人格自己的 27B 质量模型整理；只读取主人原话，每条事实必须回溯到真实消息编号，新更正优先于旧说法。
5. SQLite 保存完整对话原文、用户上传图片路径、会话摘要、两套人格档案、两套经历池和语义向量。助手回复按“待审计 / 可召回 / 已隔离”分层：低质量回复的原文仍保留，但不会进入 RAG。自动屏幕观察的截图是例外：它从原生客户端以内存 JPEG 交给模型，数据库和磁盘都不保存图像。

两个人格的用户档案初始为空，不内置示例个人资料。它们只会从你实际与该人格的对话中逐步构造；明确要求记住的账号、密码、API Key、Token 等字符串也会按原文保留，并在相关话题中通过档案或历史原文检索提供给主模型。

持久档案的新事实会附带“最近确认”时间；语义召回的旧会话也会将原始时间一起交给主模型，用于区分最新状态和过期信息。

新建对话只会重置“当前会话上下文”。人格档案和人格池检索仍然有效。删除对话会回收其原文、图片和向量空间，但不会自动清空人格档案；人格档案需在“记忆”页单独编辑或重建。

### 人格记忆池如何驱动行为

两套记忆不是共用资料库。一次与艾莉的用户对话只进入艾莉的对话原文层；一次与沙雅的用户对话只进入沙雅的原文层。她们共同经历的茶话和文件观察会以各自视角分别写入两套池；看屏幕后，艾莉与沙雅也会各自生成一份文字观察。所有记录都有发生时间与来源类型。

回答用户、茶话选题和文件选题时，程序会先从当前说话者自己的池中检索少量相关经历，再交给当前模型。不会把另一人格的私人对话或一份共享“大杂烩”直接塞进提示词。极短寒暄默认不召回旧事件，避免刚说“你好”就突然续聊无关旧话题；明确询问过去发生的事时仍会正常检索。

结构化“关于主人”的档案只从主人亲自说过的话整理，避免把两人闲聊中的推测误写成主人事实；茶话、文件与屏幕内容则作为带来源的亲历保存在人格池。两者共同构成长期记忆。

## 后台茶话室与自主学习

茶话室是一套独立的空闲调度器，不是永久占用 CPU 的常驻生成任务。默认策略为：

- 键盘和鼠标至少 15 分钟无操作，并且客户端没有用户请求，才能开始。
- 两轮之间随机冷却 3–6 小时，每天最多 4 轮。每两条互答后，艾莉和沙雅会分别调用自己的当前档模型，以结构化 JSON 判断 `CONTINUE` 或 `END`；只有双方都想继续才会再聊，因此没有固定发言条数。
- 可用内存和 CPU 足够宽裕时才运行；自动策略把 9B 作为空闲时的默认质量基线，只在资源明显收紧时降到 4B。27B 正在内存中时必定跳过。
- 用户回来、发起 GUI/API 对话、内存下降或 CPU 压力升高时，后台会在当前短发言结束后立即让出，不再开始后续发言。
- 连续失败或中断后至少冷却 30 分钟，防止错误时反复重试烧机器。

文件学习默认覆盖用户目录、`/Applications` 与已挂载外接盘，排除 macOS 系统目录、模型块、版本库内部目录和构建缓存。程序先根据修改时间、文件类型、是否读过和文件名筛选，再让艾莉对应的低审查 4B/9B 选题，避免官方小模型拒答中断艾莉的学习链。文本、代码、PDF/Word/RTF 和小图片可被只读观察；原文件不会被修改。

每轮会在三种模式之间选择：“随手发现”只读观察新文件，“随性闲聊”从观点或脑洞话题自然开场，“回忆旧话题”从两人各自的池中用 RAG 找回有关系的旧交流。纯闲聊不会被旧文件话题强行劫持；完整茶话和观察都会保存时间并建立向量索引，规模增长后仍只按相关性取少量内容，不把全部历史塞给 4B/9B。

文件观察会分别存入艾莉和沙雅的经历池，每条保留来源路径、文件修改时间、观察时间和“文件明示 / 可能推测”区分。它不会冒充“主人亲口确认”的事实，也不会串写两套结构化用户档案。文件选题器本身也会参考艾莉自己的近期记忆，优先寻找能延续既有经历或产生新话题的内容。

茶话室内，两人知道共同服务的是“主人”，但主人不在场时只对彼此自然说话。程序级质量门会消除人称歧义、拒绝索权和伪造执行承诺，拦截凭空出现的现实经历、作品名、线下邀约与工作会议式盘问，并限制连续追问；性格由提示词自然表达，程序不强塞“哼、啧”等口癖。两条链路绝不串模型家族：4B 候选稿不合格时先升同人格 9B，最终才用同人格 27B 短上下文重写；艾莉的无审查内容不交给沙雅官方模型审查。

已经开始的茶话不会因为主人移动鼠标、敲键盘、打开客户端或刷新页面而停止；这些活动只影响下一轮能否自动开始。只有主人真正向艾莉或沙雅发送聊天消息（包括兼容 API 的聊天请求），才会记录为“主人发来消息，用户打断了对话”并立刻在下一次发言前让路。已产生的每句话会同时进入艾莉和沙雅各自的可检索经历池；下一轮会优先带入这段未完成上下文，让她们自然决定续上还是转到新话题。

茶话没有固定长度，但也不会无限塞满模型上下文。最近消息保留原文参与生成，较早消息由本地模型滚动压缩为临时摘要；数据库和两套人格记忆池仍逐条保存原文。每次发言和结束判断之间都会重新检查 CPU、内存及主人消息，资源变紧时会安全停止并卸载本轮模型。

在“设置与管理 → 茶话室”中可以：总开关、改空闲门槛、调整最短/最长间隔和每日上限、固定 4B/9B 或使用自动档、编辑可观察路径、手动运行一轮、刷新日志，以及单独清空茶话和学习记忆。

## 低频屏幕观察

原生客户端会定期向本地服务询问是否该看一眼屏幕。默认随机间隔为 60–180 分钟、每天最多 6 次；必须是主人正在使用电脑、没有对话请求、没有其他后台轮次、CPU 与可用内存合适且 27B 未占用时才会开始。一般失败后至少等待 30 分钟；若缺少 macOS 录屏权限则退避 12 小时，不会循环狂截。也可以在“设置与管理 → 茶话室”中修改间隔、关闭功能或点击“现在看一眼”。

一次观察的生命周期是：原生客户端用 ScreenCaptureKit 在不激活窗口、不切换 Space 的情况下逐个读取所有已连接显示器 → 每屏在内存中缩放到最长边 1600 像素并压缩为 JPEG → 同一轮同时交给艾莉 9B 与沙雅 9B 观察 → 两人基于同一组屏幕继续对话，并各自判断何时结束 → 图像引用立即释放。全屏应用不会被顶出，多显示器也不会只看主屏。截图没有文件名、保存路径或数据库字段，日志只显示文字。屏幕事实审查始终使用当前说话人自己的模型链路。

为长期运行控制体积，详细屏幕经历保留 30 天，同时追加到每个人格各自的每日文字日记；旧细节到期后会连同向量删除，但每日日记继续参与检索。可见屏幕日志保留 90 天。点击“清空屏幕观察文字”会清除日志、两套池中的屏幕细节和每日屏幕日记；因为截图从不落盘，所以没有图片缓存要清理。

首次使用时，请在“系统设置 → 隐私与安全性 → 屏幕与系统音频录制”中允许 `星语茶话屋`，然后按系统提示重启客户端。后台轮询只使用无副作用的权限预检，绝不会自动反复调用系统授权弹窗；需要时可在设置中手动打开对应系统页面。关闭权限后，普通对话、API、茶话室和文件观察仍然工作，只会跳过屏幕观察。

建议始终使用 `星语茶话屋.app`。`启动器/` 里的 `.command` 只作为兼容的终端入口；终端模式无法上传图片。

终端命令：

```sh
ollama run qwen3.5:4b-16k
ollama run qwen3.5:9b-16k
ollama run qwen3.5:27b
```

低审查模型：

```sh
ollama run huihui_ai/qwen3.5-abliterated:4b-16k
ollama run huihui_ai/qwen3.5-abliterated:9b-16k
ollama run huihui_ai/qwen3.5-abliterated:27b
```

退出当前对话：输入 `/bye`。下次打开同一模型时会自动续接它上次的会话。

查看已安装模型：

```sh
ollama list
```

为了在 24GB 统一内存上保持稳定，建议一次只运行一个模型。4B/9B 的本地别名已配置 16K 上下文和最多 2048 输出 token；高级 27B 继续使用 4K。高级档使用时尽量关闭大型游戏、虚拟机和大量浏览器标签页。

上下文本身不可能真正无限。本客户端的“无限对话”逻辑是：原文归档；每个长会话在窗口快满时滚动摘要；每个人格持续维护结构化档案与自己的经历池；每次提问再从该人格的对话原文、茶话、文件和屏幕经历中语义召回相关片段。最终给主模型的是“人格设定＋结构化档案＋相关经历＋本会话摘要＋最近原文”，而不是无限堆叠消息。

均衡与快速模式关闭 Thinking，为正文预留输出空间。深度模式会启用 Thinking；如果某个模型把整个输出预算耗在思考区而没有产生正文，统一推理层会携带未完成推理草稿自动恢复，并在性能信息里标记 `recovered_from_thinking_limit`。因此不会再把空白回复保存进会话，也不会因为一次思考耗尽破坏后续对话。

### 长对话命令

| 命令 | 作用 |
| --- | --- |
| `/new [名称]` 或 `/clear` | 开始新会话，保留旧会话 |
| `/sessions` | 列出当前模型的会话 |
| `/switch ID` | 续接指定会话 |
| `/history 20` | 查看最近 20 条原文 |
| `/memory` | 查看当前长期摘要 |
| `/storage` | 查看会话数、消息数和占用 |
| `/delete ID` | 删除一个会话并回收空间 |
| `/cleanup 30` | 删除当前模型 30 天未使用的会话 |
| `/cleanup all` | 清理当前模型的所有历史 |

## API 调用教程

现在有两个互不冲突的入口：

| 地址 | 用途 |
| --- | --- |
| `http://127.0.0.1:11434` | Ollama 原生 API；保留原有的全部功能和参数 |
| `http://127.0.0.1:11435/v1/` | OpenAI 兼容的双人格记忆 API；自动注入当前人格档案及其独立记忆池召回结果 |

打开 `星语茶话屋.app` 后两个 API 都会自动就绪。只需 API 而不打开界面时，可使用 `启动器/启动长期记忆API.command`。

Ollama 启动后，本地 API 地址是 `http://127.0.0.1:11434`，只监听本机。

### 1. cURL：最简单的调用

```sh
curl http://127.0.0.1:11434/api/chat \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "huihui_ai/qwen3.5-abliterated:9b-16k",
    "messages": [
      {"role": "system", "content": "你是一个高质量中文助手。"},
      {"role": "user", "content": "写一段杭州雨夜的短篇开头。"}
    ],
    "stream": false,
    "think": false,
    "options": {"num_ctx": 16384, "num_predict": 2048}
  }'
```

把 `model` 换成上面任意一个已安装模型名即可。`stream: false` 会一次返回完整 JSON；删除它或改为 `true` 可逐 token 流式返回。

### 2. Python：Ollama 官方 SDK

安装一次依赖：

```sh
python3 -m pip install ollama
```

```python
from ollama import Client

client = Client(host="http://127.0.0.1:11434")
response = client.chat(
    model="huihui_ai/qwen3.5-abliterated:9b-16k",
    messages=[
        {"role": "system", "content": "你是一个高质量中文助手。"},
        {"role": "user", "content": "用三点解释量子纠缠。"},
    ],
    think=False,
)
print(response.message.content)
```

### 3. 兼容 OpenAI SDK（无长期记忆的标准调用）

已有使用 OpenAI SDK 的项目，只需修改 `base_url` 和模型名：

```sh
python3 -m pip install openai
```

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:11434/v1/",
    api_key="ollama",  # 本地服务会忽略，但 SDK 要求非空
)

response = client.chat.completions.create(
    model="huihui_ai/qwen3.5-abliterated:9b-16k",
    messages=[{"role": "user", "content": "你好，请介绍你自己。"}],
)
print(response.choices[0].message.content)
```

查看 API 能看到的模型：

```sh
curl http://127.0.0.1:11434/v1/models
```

不要直接把 `11434` 端口暴露到公网；Ollama 的本地接口默认没有访问密码。如需跨设备使用，应在前面加带认证和 HTTPS 的反向代理。

### 4. 双人格长期记忆 API

模型名会自动决定人格：低审查三个模型属于艾莉，官方三个模型属于沙雅。也可以显式传入 `"persona": "aili"` 或 `"persona": "shaya"`，服务会校验人格与模型是否匹配，错误组合直接返回 400，防止串人格。

首次请求不传 `conversation_id`：

```sh
curl http://127.0.0.1:11435/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "huihui_ai/qwen3.5-abliterated:9b-16k",
    "persona": "aili",
    "messages": [{"role": "user", "content": "请记住：我喜欢翡翠色。"}],
    "stream": false
  }'
```

返回 JSON 顶层和 `X-Conversation-ID` 响应头都包含会话 ID。下一次只发新消息并带上该 ID：

```json
{
  "model": "huihui_ai/qwen3.5-abliterated:9b-16k",
  "persona": "aili",
  "conversation_id": 12,
  "messages": [{"role": "user", "content": "我喜欢什么颜色？"}],
  "stream": false
}
```

可直接运行同目录的无依赖完整示例：

```sh
python3 /Users/konako/项目/本地AI/示例/api_memory_example.py
```

OpenAI Python SDK 完整示例：

```python
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:11435/v1/", api_key="local")

first = client.chat.completions.create(
    model="huihui_ai/qwen3.5-abliterated:9b-16k",  # 艾莉·日用档
    messages=[{"role": "user", "content": "记住这个项目的新名字：星海。"}],
    extra_body={
        "persona": "aili",
        "conversation_title": "项目命名",
        "quality_mode": "deep",
        "top_p": 0.95,
        "repeat_penalty": 1.1,
        "seed": 0,
        "keep_alive": "10m",
    },
)
conversation_id = first.model_dump()["conversation_id"]

second = client.chat.completions.create(
    model="huihui_ai/qwen3.5-abliterated:9b-16k",
    messages=[{"role": "user", "content": "刚才确定了什么名字？"}],
    extra_body={"persona": "aili", "conversation_id": conversation_id},
)
print(second.choices[0].message.content)
```

可用的增强参数：

| 参数 | 可选值 / 范围 | 作用 |
| --- | --- | --- |
| `quality_mode` | `fast` / `balanced` / `deep` | 快速、均衡、深度三档；默认 `balanced` |
| `think` | `true` / `false` | 显式覆盖质量档的 Thinking 开关 |
| `temperature` | `0`–`2` | 越低越稳定，越高越发散 |
| `top_p` | `0.05`–`1` | 控制候选词采样范围 |
| `repeat_penalty` | `0.8`–`2` | 抑制重复用语 |
| `seed` | 整数 | 固定为非零值便于复现；`0` 使用默认随机行为 |
| `keep_alive` | 如 `10m`、`1h`、`0` | 模型完成后在内存中的驻留时间 |
| `max_tokens` / `max_completion_tokens` | 正整数 | 单次输出上限；深度模式至少预留 1024 |

非流式返回的顶层 `local_metrics`、流式结束事件中的 `local_metrics`，以及客户端保存的助手消息元数据，都会包含记忆命中、上下文占用、首字时间、总耗时、生成速度和是否发生自动恢复。标准 SDK 不认识的参数请放在 `extra_body` 中。

`conversation_id` 控制的是当前会话原文和连续上下文。即使第三方应用不保存它，每个请求会成为一个新会话，但艾莉或沙雅自己的结构化档案与独立人格池检索仍然有效。API 对话和客户端对话走同一套 SQLite 与 RAG，因此也会进入对应人格的记忆。

查询人格、共享记忆状态和档位映射：

```sh
curl http://127.0.0.1:11435/v1/personas
curl http://127.0.0.1:11435/v1/models
```

返回的 `pending_messages` 表示有多少条新原文等待后台整理；`memory_pool` 会显示该人格的非会话经历数量、向量数量和来源分布。助手原文另有待审计状态，通过同人格 14B 事实门后才进入召回向量；用户原话不等待这一层。

### 5. 会话管理和空间清理 API

```sh
# 查看会话和数据库占用
curl http://127.0.0.1:11435/v1/conversations
curl http://127.0.0.1:11435/v1/storage

# 永久删除会话 12，随后自动 VACUUM 回收空间
curl -X DELETE http://127.0.0.1:11435/v1/conversations/12 \
  -H 'X-Confirm-Delete: DELETE'

# 删除指定模型 30 天未使用的会话
curl http://127.0.0.1:11435/v1/admin/cleanup \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "qwen3.5:9b-16k",
    "older_than_days": 30,
    "confirm": "DELETE"
  }'
```

清理只删除命中的会话、附件和对应语义向量，不会删除六个对话模型、向量模型、两个 14B 隐藏协同模型或两套人格档案。所有服务只监听 `127.0.0.1`。
